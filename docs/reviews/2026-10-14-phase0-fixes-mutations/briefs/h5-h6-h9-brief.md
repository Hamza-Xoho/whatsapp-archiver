## H5 (verbatim)
The hand-built `events.Message` skips what `Client.ParseWebMessage` does (Table 2 lists it; Task 6 says to use it). Lost or wrong: (a) wrapped messages (ephemeral, view-once, document-with-caption) are not unwrapped, so `text` is empty and no media row is queued (live path unwraps via `UnwrapRaw`); (b) sender of own messages is the other party in a DM, and the group JID in a group (and the group JID is inserted into `participants`); (c) `PushName` is dropped; (d) `key.participant`-only fallbacks and thread metadata are ignored. Note `ParseWebMessage` rewrites edits to the original ID, so naive use would lose edits: handle `MESSAGE_EDIT` before calling it.
Red tests (names fixed): `TestHistoryEphemeralAndDocumentCaptionAreUnwrapped`, `TestHistoryFromMeMessageHasOwnJIDAsSender`, `TestHistoryPushNameIsStored`, `TestHistoryEditIsStillAnEvent`.

## H6 (verbatim)
(a) `UpsertChat` overwrites the name with the empty string on every message, so a name learned from history is wiped within the same import. (b) `ImportHistory` upserts the chat and its name before the exclusion filter, so an excluded chat's JID and name are written to `chats`. Fix: upsert name only when non-empty (`COALESCE(NULLIF(excluded.name,''), name)`); move the history chat upsert behind the filter. Red tests: `TestLiveMessageKeepsKnownChatName`, `TestExcludedChatNameNotStoredFromHistory`.
Carried from the B1/H2 review (do these in the H6 cycle, with their own red tests): (i) `UpsertChat`, `UpsertParticipant`, `InsertMedia` and the alias-check/commit errors inside `InsertMessage` bypass `store.classify`, so a constraint error there loops forever at 160 ms — route them through `classify`; (ii) `persist`'s retry-forever loop must switch to the permanent path if `isPermanent(err)` becomes true mid-loop; (iii) `TestOtherErrorsAreNotConstraintErrors` uses a non-sqlite error — add a negative test with a real non-constraint `*sqlite.Error` (e.g. SQLITE_BUSY from a second connection holding a write lock, or another cheap real error) and a positive test through `insert()`.

## H9 (verbatim)
The chunk ID is a hash of `(sync type, chunk order, progress, conversation count)`, so two different chunks with the same numbers (very likely across a re-pair) collide and the second ledger row is silently dropped by `ON CONFLICT DO NOTHING`. Fix: include `received_at` (or a counter) in the ID, or drop the unique ID and use an autoincrement key. Red test: `TestTwoDistinctChunksWithSameProgressAreBothLedgered`.
