## H1 (verbatim)
Every `InsertMessage` materialises the whole `chat_aliases` view (a full scan of `messages`) because the alias check filters on `x.id`, which is not the primary-key prefix. Insert cost grows with table size, so a long history import is quadratic and live messages slow down as the archive grows (≈3 h for 500k messages, 12 h for 1M on this Mac). Measured: 5k-row batches at 2,250, 1,165, 808, 579, 438, 404 inserts/s; `EXPLAIN QUERY PLAN` shows `MATERIALIZE chat_aliases` / `SCAN messages`. Fix: look up aliases of the one chat first (tiny), then probe `messages` by `(chat_jid IN (…), id)` on the primary key. Failing test first: `TestInsertMessageCostDoesNotGrowWithTableSize` (e.g. 20k inserts under a time budget, or assert the plan contains no `MATERIALIZE`).
Plan (Task 2): "The alias check in `InsertMessage` reuses the `chat_aliases` view" — this ruling supersedes it for the hot path: the per-insert check uses an indexed lookup of the one chat's aliases; the view stays for read paths.
