# WhatsApp Archiver V1 plan: a reliable logger with a chats UI

Written 26 Oct 2026. Repo: `/Users/hamza/Code/whatsapp-archiver/archiver` (Go, `make` only). First execution step: copy this file to `docs/plans/2026-10-26-v1-plan.md` and commit it.

## Context

A one-week run of two instances (20–26 Oct, report `docs/reviews/2026-10-26-week-review-issues.md`) found:

- A 7h20m capture outage that sent no alert.
- 12 new decryption gaps.
- 25k media rows `failed`.
- History stuck at 99%.
- A practice instance using 18% CPU on average.
- Phase 2 acceptance mostly open.

Hamza has re-scoped V1 (answers of 26 Oct 2026):

- **V1 is a logger, not an intelligence platform.** It must log accurately, efficiently and reliably. It records and shows its own progress, stores every data type properly in the database, and has a UI with three areas: **Chats** (a very good viewer: chosen-chat sync control, WhatsApp-like reading, search, filters, jump to date, export), **Logging** (health and progress) and **Pairing**.
- **Out of V1:** modules, jobs, transcription, translation, MCP, the wizard and release packaging (GoReleaser, Homebrew, Docker, SC-8). They move to "after V1" in the charter.
- **Reliability means engineering around outages,** not just alerting: detect them, route around them, record them, deliver alerts late, and verify the backlog afterwards.
- **Old data is discarded.** The schema may be redesigned freely and migrations squashed. The old archive is deleted only after V1 is confirmed working on ryzen.
- **Old media:** fix the code (403 counts as expired) and do not chase the old rows.
- **Access:** SSH tunnel to a loopback port, no login. The practice instance is stopped and unlinked.
- **Trial:** a full fresh redeploy on ryzen is the V1 completion trial. The plan must include a live full-stack UI test.

## Root causes found while planning (verified in code)

| Report item | Finding | Evidence |
|---|---|---|
| 1. Outage, no alert | whatsmeow's keepalive path does a *manual* `cli.Disconnect()` and then `autoReconnect`, so **no `events.Disconnected` is emitted**. Health stays `connected`, and the `disconnected_after` rule never runs. Its `AutoReconnectHook` is unused. The `no_events` rule (6 h) should have fired at about 6 h, but ntfy shares the host's broken DNS. Also, `alertGate` marks an alert "fired" when it is queued, not when it is sent, so a failed send is not retried for 6 h. | `.cache/gomod/go.mau.fi/whatsmeow@…/keepalive.go:46-50`, `client.go:609-628,644-680`; `internal/ingest/pipeline.go:207-220`; `internal/health/health.go:171-180,296-310` |
| 3. 25k media failed | `classifyDownloadErr` treats only 404/410 as expired. A 403 (whatsmeow `ErrMediaDownloadFailedWith403`, which whatsmeow itself treats like 404/410) becomes a plain failure, is never re-requested, and dies at 20 attempts. The 803 "failed to refresh media conn" rows are outage network errors that used up their attempts (20 × 15 min is shorter than 7 h). | `internal/wa/download.go:16-24`; `internal/media/queue.go:28-33,233-255`; whatsmeow `download.go:281` |
| 5. Practice CPU 18% | Each media worker wakes every **100 ms** and runs `ClaimMedia` (a write transaction) and `requestPass` (`FailStaleRetries` plus `NextExpiredMedia`). The `media` table has **no index** on state, so the expired-row query scans and sorts with blobs. The practice instance's 2020+ history makes many `expired` rows, and the 10/min limiter makes the loop rescan endlessly. Main has 405 expired rows; practice likely has thousands. **Fixing 403 alone would put main into the same loop**, so the indexes and scheduler must land in the same change. Confirm with `perf` (W0). | `internal/media/queue.go:120-128,151-185`; `internal/store/store.go:239,252-303`; `migrations/0001_raw.sql` (no media index) |
| 4. History 99% | ADR-31 is behaving as designed: FULL chunk 47 never arrived. | 2. Gaps | Gaps cannot close for events whose own message ID is not stored (the `…6F66` case), and there is no cause column. The gaps seen after the reconnect at 01:31 fit "no sender key" and "untrusted identity" on the offline backlog. | `PROGRESS.md` Task 6; `open_gaps` view |

### W3. Connection reliability (parallel with W4; sonnet, opus review) — packages `wa`, `health`, `ingest` (state mapping only), `cmd/archiver`

1. **Reconnecting state.**
   - `AutoReconnectHook` emits `reconnect_failed{class, count}`, where the class is dns, tcp, tls, ws or other, and never contains a URL (use `logsafe`).
   - `KeepAliveTimeout` moves the state to `degraded`; `KeepAliveRestored` or `Connected` moves it back to `connected`.
   - A watchdog every 30 s: when `!IsConnected()` while the state is `connected` for 60 s, set `reconnecting`. This catches any path with no event.
   - Health treats `reconnecting` and `degraded` as down for `disconnected_after`; the default drops to 5 min.
   - Red test: a fake client that goes through the keepalive path with no `Disconnected` event must alert after the threshold. This is the regression test for report item 1.
2. **DNS fallback.**
   - An `http.Client` whose `Transport.DialContext` tries the system resolver, then the configured `network.fallback_dns` (default `1.1.1.1:53`, `8.8.8.8:53`), then a last-known-good IP cache per host (kept in memory and in `settings`).
   - Applied via `SetWebsocketHTTPClient`, `SetMediaHTTPClient` and the ntfy client.
   - First verify in whatsmeow's source that the websocket dial uses that client's transport, and record a prior-art row.
   - Test with a fake resolver that fails.
3. **Outage ledger.** Every period that is not `connected` gets a `connection_periods` row. `OfflineSyncPreview` and `OfflineSyncCompleted` counts go into the row that just closed, which verifies the backlog delivered after a reconnect. Gaps within 2 min after a reconnect are tagged `post_outage`.
4. **Durable alert outbox.**
   - `alertGate` state and the queue move to the `alerts` table, replacing the `health.json` `learnActiveAlerts` workaround.
   - The sender retries with exponential backoff (up to 1 h) until delivery. A late alert says "raised HH:MM, delivered late".
   - An alert counts as fired only once it is stored.
   - Test: ntfy failing for 2 h, then recovering, delivers both the alert and the recovery, in order.
5. **Off-host heartbeat.** Optional `alerts.heartbeat_url`, pinged every 5 min only while `connected` and events are fresh, so a healthchecks-type service alerts when ryzen itself is offline. Off when empty.
6. **systemd.**
   - `Type=notify`, `WatchdogSec=120`, `Restart=always`, `RestartSec=5`, `After=`/`Wants=network-online.target`.
   - A pure-Go sd_notify over the `NOTIFY_SOCKET` unixgram socket; no new dependency.
   - The watchdog ping is sent only while the event loop and writer are making progress.
   - `deploy/` unit and README updated.
7. **Log hygiene.**
   - The whatsmeow logger collapses repeated identical lines: the first one, then "repeated N times in 5 m".
   - Shutdown `context canceled` lines in the media queue are logged at Info (report items 8 and 10).
   - The Logging page and `archiver status` show outage minutes per day and the longest outage, replacing the D3 count.

### W4. Media pipeline (parallel with W3; sonnet) — packages `media`, `wa/download.go`, store media queries

1. `classifyDownloadErr`: 403 → expired (ADR-38). `http_status` and `error_class` are stored. The full reason is stored untruncated (redacted).
2. Network-class errors (dial, DNS, timeout, 5xx, media conn refresh) **do not use up attempts**. They reschedule with backoff capped at 15 min, and the queue **pauses while health is not `connected`** (a gate func passed in from serve; `media` must not import `health`).
3. Scheduler without polling:
   - Workers block on `wake` or a timer set to `MIN(next_attempt_at)`.
   - `requestPass` waits on `limiter.Reserve().Delay()`.
   - `FailStaleRetries` runs hourly.
   - Uses the W2 indexes.
   - Regression test: an idle queue with 10k expired rows makes at most N store calls per minute (fake clock plus a counting store wrapper). This pins report item 5.
4. Live-first stays. Metadata (filename, duration, dimensions, thumbnail) comes from the proto at enqueue.
5. SC-3 measurement: `archiver status` and the Logging page show "% of enabled media done within 5 min" over 24 h and 7 d.

### W5. History and gaps (sonnet; opus review of the ADR-37 change)

1. **Spool.**
   - The handler downloads the blob (bounded) and writes the `history_spool` row plus a `received` ledger row in one transaction, then acks.
   - An importer goroutine imports spool rows in order through `Pipeline.Ingest` and marks them imported; it resumes after a restart.
   - Live messages no longer queue behind an import.
   - Tests: a crash between spool and import re-imports with no duplicates; a live message during a 50k-message import is stored in under 1 s.
2. **History status.**
   - Per sync type in the ledger, plus "stalled at N% (no chunk for 48 h)", which is not called "in progress".
   - Per-chat "back to" from `chat_stats.oldest_history_ts`.
   - `view.HistoryLine` and the UI updated.
3. **Gaps.** The cause is recorded from whatsmeow's undecryptable info. Closing on `source_id` (from W2) is pinned with the `…6F66` and `…FCCF` cases from Task 6 as tests. The Logging page lists open gaps by cause and age.
